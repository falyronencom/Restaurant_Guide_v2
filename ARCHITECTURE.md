## 1. Карта системы

```
 mobile (Flutter)         web (Next.js 16, SSR)        admin-web (Flutter Web)
 гость: поиск, карта,     витрина, каталог, поиск,     модерация карточек,
 карточка, бронь;         карта; кабинет заведения;    отзывы, позиции меню,
 кабинет заведения        личный раздел                здоровье данных
        │                        │ с сервера сайта           │
        └────────────────────────┼───────────────────────────┘
                                 │ HTTPS /api/v1
                                 ▼
             backend (Node.js 20, Express, SQL через pg, без ORM)
      маршрут → контроллер → сервис (правила) → модель (SQL) → проекция
      в том же процессе: очередь распознавания меню, чистка токенов
         │                       │                         │
 PostgreSQL 16 + PostGIS   Redis 7: лимиты,       Cloudinary (файлы) · OpenRouter
 (и очередь ocr_jobs)      кэш разбора фраз       (модели) · Resend · Firebase
```

Карты Яндекса и вход через Google и Яндекс работают на клиентах; API только проверяет токен провайдера. Панель написана на Flutter Web и ходит в API из браузера; её адрес внесён в `CORS_ORIGIN`.

**Гость: поиск → карточка → меню и бронь.** Фраза из строки поиска уходит в `POST /api/v1/search/smart` (решение 7), без фразы работает каталог с фильтрами. Карточка в приложении — `GET /api/v1/search/establishments/:id`, на сайте — адрес `/{город}/{категория}/{slug}` и `GET /api/v1/public/establishments/by-slug/:slug`. Меню на сайте — распознанные позиции и исходные файлы, в приложении — фото и PDF. Бронь — только в приложении и у заведения, которое её включило; заявку без ответа система закрывает сама.

**Заведение: кабинет → модерация → публикация.** Мастер карточки есть на сайте (`web/src/app/(cabinet)`) и в приложении. Карточка создаётся черновиком и уходит на модерацию (`POST /api/v1/partner/establishments`, `…/:id/submit`). Модератор одобряет её или отклоняет с замечаниями по полям (`POST /api/v1/admin/establishments/:id/moderate`). Публично видны только карточки `active`; правки одобренной карточки выходят без повторной модерации.

**Меню: фото или PDF → распознавание → позиции → поиск.** Файл уходит в Cloudinary, задача — в таблицу `ocr_jobs`. Обработчик в процессе API берёт задачи по одной (`FOR UPDATE SKIP LOCKED`). Модель читает страницы как картинки, вторым вызовом раскладывает текст в позиции, а детерминированная проверка помечает сомнительное (`backend/src/services/ocr/`). Позиции заменяют прежние одной транзакцией. Прерванная задача возвращается в очередь, пока не кончились попытки. Позиции видны на сайте и ищутся по блюду, помеченные уходят модератору.

## 2. Ключевые решения

### 1. Публичный ответ собирает проекция-перечень

**Решение.** Публичные ответы о заведениях, отзывах и позициях меню собирают проекции — чистые функции с перечнем разрешённых полей. Проекции разделены по виду ответа (карточка, строка списка, метка карты) и живут в одном модуле для приложения (`/api/v1/search/*`) и сайта (`/api/v1/public/*`). Поля, без которых приложение не разберёт ответ, закреплены тестом сервера.

**Почему.** Запрос к базе отдаёт строку целиком, с контактами владельца и заметками модерации; перечень не выпустит и новую колонку. Когда из ответа выпало `updated_at`, установленное приложение перестало открывать список, а тест был зелёным: он утверждал, что поля нет.

**Что отвергли.** Две параллельные поверхности API со своими правилами полей: они расходились бы при каждой правке. Тесты только на исключённое.

**Чем платим.** Новое поле — правка проекции и типов сайта одним коммитом. Обязательное поле не убрать без новой сборки приложения.

**Где в коде.** `backend/src/projections/`, `backend/src/tests/integration/mobile-wire-contract.test.js`. Журнал: CAT-D-1.2, CAT-D-1.3, CAT-D-1.10, CAT-E-1.1.

### 2. Данные о заведении публичны, о владельце — закрыты

**Решение.** Публично то, что заведение вывешивает у входа: название, адрес, телефон, часы, фото, меню; отзывы — с именем и аватаром автора из его профиля. Реквизиты, документы и контакты владельца, заметки модерации и служебные признаки закрыты. Роль `viewer` нужна, чтобы показывать панель посторонним: в панели она только читает, а личных данных ей не отдают — контактов и документов партнёров, e-mail авторов отзывов, IP из журнала действий.

**Почему.** Сведения о владельце нужны только модератору, а контакты партнёров третьим лицам не передаются по закону № 99-З «О защите персональных данных». Кнопки панели действуют на живые заведения.

**Что отвергли.** Прятать кнопки только в интерфейсе. Ступени доступа держит API, а маршрут без ступени роняет тест.

**Чем платим.** Каждый новый ответ панели надо проверять на поля, не положенные просмотрщику.

**Где в коде.** `backend/src/config/panelRoles.js`, `backend/src/routes/v1/adminRoutes.js`, `backend/src/tests/unit/adminRoutesAccessTiers.test.js`. Журнал: CAT-C-4.1, CAT-C-2.11.

### 3. Сеансы: refresh с окном 60 секунд, access сверяется с базой

**Решение.** Access-токен — JWT на 4 часа, refresh — одноразовый, на 30 дней. Повтор refresh, погашенного обновлением, в течение 60 секунд (умолчание настройки) получает того же, ещё живого преемника; любой другой повтор гасит все сеансы. `authenticate` сверяет аккаунт с базой (кэш — 10 с); после сброса пароля прежние токены получают 401 `TOKEN_REVOKED`.

**Почему.** Сам JWT не узнает, что аккаунт отключён или пароль сброшен. Строгая одноразовость путает кражу с потерянным ответом: клиент повторяет погашенный токен сам. 60 секунд выведены из поведения клиента: таймаут приёма — 30 с, худший повтор приходит примерно через 31 с.

**Что отвергли.** JWT без обращения к базе. Ротацию без окна. Раннюю чистку погашенных токенов: по ним распознаётся повтор.

**Чем платим.** Запрос по первичному ключу раз в 10 секунд на аккаунт. Без базы ответ — 503, а не 401.

**Где в коде.** `backend/src/config/auth.js`, `backend/src/services/authService.js`, `backend/src/middleware/auth.js`, `backend/src/services/accountStatus.js`. Журнал: CAT-D-2.1, CAT-D-2.2; миграция 035.

### 4. Сайт — сервер между браузером и API

**Решение.** Браузер посетителя к API не обращается: адрес API знает только сервер Next.js, токены лежат в httpOnly-cookie сайта. Код входа через Яндекс меняется на токен на сервере сайта, и в API уходит тот же запрос, что из приложения. Операции кабинета — Route Handlers с обычным JSON, а не Server Actions.

**Почему.** Контракт входа один, секрет Яндекса хранится в одном сервисе, CORS не нужен. Потоковые ответы (Server Actions, RSC) на Railway временами получали 503 на краю сети, хотя сервис отвечал 200. Обычного JSON это не касается.

**Что отвергли.** Принимать `code` на backend — это вторая форма входа. Cloudflare против 503: POST идёт мимо кэша через тот же край сети.

**Чем платим.** Лишний шаг браузер → сайт → API. Проверку источника запроса (CSRF) каждый обработчик делает сам.

**Где в коде.** `web/src/lib/api/client.ts`, `web/src/lib/auth/yandex.ts`, `web/src/app/api/`, `web/src/lib/partner/same-origin.ts`. Журнал: CAT-C-3.3, CAT-C-3.6.4, CAT-C-3.9, CAT-C-3.14.

### 5. CI перед выкаткой, одна платформа

**Решение.** Pull request и push в `main` проходят пять задач CI: backend (lint и тесты на настоящих PostgreSQL + PostGIS и Redis), сторож уязвимостей зависимостей, сайт, mobile и admin-web. Railway выкатывает API, сайт и панель только после зелёного CI (настройка «Wait for CI»). Почему тесты идут под двумя часовыми поясами — в README.

**Почему.** 19.08.2026 набор тестов перестал загружаться из-за импорта без мока: 76 тестов пять дней не шли, а прогон возвращал код 0. Такое ловит только независимый прогон. Одна платформа — это одни логи, переменные и счёт.

**Что отвергли.** Выкатку, которая держится только на дисциплине. `next build` против рабочего API: гейт краснел бы от чужого простоя. Плавающую версию Flutter. Vercel рядом с Railway.

**Чем платим.** Ошибки пререндера видны только при сборке на Railway. Приложение собирается вручную. Настройки сервисов Railway, включая ожидание CI, живут в его панели, а не в репозитории.

**Где в коде.** `.github/workflows/ci.yml` (причины записаны у шагов), `backend/railpack.json`, `admin-web/Dockerfile`. Журнал: CAT-C-4.4, CAT-C-3.8.

### 6. Миграции — вручную после выкатки

**Решение.** Код выкатывается сам, а миграцию оператор применяет позже, скриптом с подтверждением. Поэтому новая колонка приходит с кодом, который работает и без неё: при чтении её отсутствие даёт `NULL` (`to_jsonb(users) ->> …`), запись идёт под точкой сохранения. `production_schema.sql` — снимок рабочей базы, а не каталога миграций; CI докатывает на него свежие миграции.

**Почему.** Между выкаткой и миграцией новый код видит старую схему. Колонка, названная в `SELECT`, роняла бы каждый запрос; для миграции 035 — каждый запрос с авторизацией.

**Что отвергли.** Полагаться на порядок «сначала миграция, потом код». Вносить в снимок неприменённую миграцию 030: 02.09 это уронило CI.

**Чем платим.** Код сложнее, и нужен тест «без колонки». Снимок ведётся руками и может отставать от рабочей базы.

**Где в коде.** `backend/scripts/apply-migration-production.js`, `backend/migrations/production_schema.sql`, `backend/src/tests/integration/session-revocation.test.js`. Правило записано в шапках миграций и снимка схемы.

### 7. Умный поиск: модель разбирает фразу, ищет SQL

**Решение.** Модель через OpenRouter только переводит фразу в фильтры: тип, кухню, блюдо, приём пищи, бюджет, город, удобства. Выдачу считает тот же SQL, что у каталога. Разбор кэшируется в Redis на час по хэшу фразы; фильтры и страница в ключ не входят. Название заведения сверяется с базой без модели, блюдо ищется по основам слов. Без ответа модели поиск идёт по самой фразе с пометкой `fallback`.

**Почему.** Платим за новую фразу, а не за каждый запрос, и один движок даёт одну выдачу на всех экранах. Одно и то же слово модель читает по-разному: из 20 разборов «Pigeon» 15 вышли пустыми. Поиск по основам нашёл 94,9 % пар «запрос × заведение» на копии меню, поиск фразой — 79,1 %.

**Что отвергли.** Модель на каждый запрос. Только фильтры. Два движка.

**Чем платим.** Первый разбор новой фразы ждёт модель, до 20 с. Модели уходят из каталога поставщика, поэтому сроки раз в неделю проверяет workflow. Модель и промпт меняют только вместе, после замера.

**Где в коде.** `backend/src/services/smartSearchService.js`, `backend/src/utils/establishmentNameMatch.js`, `.github/workflows/model-expiry.yml`. Журнал: CAT-C-2.2.

### 8. Адрес и словари: строгая запись вместо терпимого чтения

**Решение.** Адрес карточки — `/{город}/{категория}/{slug}`. Slug — транслит названия по образцу BGN/PCGN, с белорусскими `і` и `ў`; он уникален. После публикации переименование его не меняет, поправить slug может только модератор. Категории и кухни записываются только значениями закрытых словарей (15 и 12, по-русски), их проверяют валидатор и сервис по одному словарю. Словарь удобств — 10 ключей; выбранные удобства фильтруются по «И», категории и кухни — по «ИЛИ».

**Почему.** Опубликованный адрес раздают и индексируют. На первой категории держатся sitemap, выдача каталога и сам адрес. Неканоничное значение ломает их молча, а по прямой ссылке карточка открывается.

**Что отвергли.** «Терпимое выведение» slug категории из старых и английских значений при чтении: оно чинит один путь из трёх и прячет симптом. UUID в адресе, префикс языка.

**Чем платим.** Переименованное заведение живёт со старым адресом, редиректов нет. Ограничение в базе (миграция 030) готово, но на рабочем сервере не включено до замены временных данных. Ключи удобств при записи не проверяются: мастер приложения пишет три ключа по-старому.

**Где в коде.** `backend/src/utils/slugGenerator.js`, `backend/src/constants/urlSlugs.js`, `backend/src/constants/establishmentVocab.js`, `backend/migrations/030_category_cuisine_canon_check.sql`. Журнал: CAT-C-2.9, CAT-C-3.4, CAT-C-3.15, CAT-D-1.1, CAT-D-1.4, CAT-D-1.9.

### 9. PDF-меню читается картинками

**Решение.** Каждая страница PDF рендерится в картинку и читается моделью отдельным вызовом, все страницы — параллельно; текст каждой страницы та же модель вторым вызовом раскладывает в позиции. Текстовый слой берётся только на последней попытке, если картинка не прочиталась, и это пишется в журнал с уровнем error.

**Почему.** Текстовый слой не держит раскладку: цены колонкой приходят отдельным блоком, и модель угадывает, чья цена чья. На рабочих карточках так вышло 15 чужих цен из 35 в одном меню и 17 — в другом. Картинкой те же страницы прочитались почти без ошибок в ценах: со сверкой глазом совпали, например, 47 из 47 и 71 из 73.

**Что отвергли.** Перечитывать картинкой, когда цен меньше половины: так ловились пустые цены, но не чужие. Один вызов на документ: он путал порядок страниц.

**Чем платим.** Каждая страница — отдельный вызов модели, а это дороже чтения текстового слоя.

**Где в коде.** `backend/src/services/ocr/ocrService.js` (`extractPageTexts`, `readPagesAsImages`), `backend/src/tests/integration/ocr-pipeline.test.js`. Коммиты `0c7f03d` и `ffd1d4f`, 29.09.2026.

### 10. ИИ помечает, решает человек

**Решение.** Сам ИИ только разбирает фразу и распознаёт меню. Результат проходит детерминированные проверки: разбор фразы — схемой Zod, позиция меню — порогом уверенности 0,70, границами цены 0,50–1000 BYN и скачком цены больше чем втрое. Сомнительное помечается, а не скрывается. Публикует карточки, скрывает отзывы и позиции только человек; «Здоровье данных» в панели работает без моделей. Во внешние модели уходят только фраза поиска, без идентификатора пользователя, и страницы меню.

**Почему.** Самостоятельность задачи ограничена ценой её худшей ошибки; для маленькой площадки ложное удаление дороже пропуска. Тихое скрытие спрятало бы данные от модератора, а проверка той же моделью подтверждала бы её же ошибки. Модели работают вне Беларуси, а персональные данные охраняет закон № 99-З.

**Что отвергли.** Автоматическое одобрение, скрытие и удаление: только после измеренного согласия с человеком и с учётом закона. Автоскрытие по порогу уверенности.

**Чем платим.** Работа модератора растёт с каталогом. Помеченная позиция видна гостю с пометкой, пока её не скроют.

**Где в коде.** `backend/src/services/ocr/sanityChecker.js`, `backend/src/projections/menuItemProjections.js`, `backend/src/models/qualityHealthModel.js`. Журнал: CAT-F-1…CAT-F-6, CAT-C-2.7.

### 11. Рейтинг — байесовское среднее

**Решение.** В каталоге и поиске сортировка «по рейтингу» идёт по взвешенной оценке `(v·R + m·C) / (v + m)`, где `m = 5`, `C = 3,5`; на карточке — настоящая средняя оценка и число отзывов. «По расстоянию» — по метрам. Других множителей и ручных поправок в сортировке нет: колонка `boost_score` осталась от ранней схемы и в формулы не входит. В умном поиске совпадения по названию заведения ставятся впереди (решение 7).

**Почему.** 5,0 при одном отзыве не должна обгонять 4,8 при двухстах. `C` — константа, а не среднее по площадке, поэтому не плывёт вместе с данными. Честная выдача — принцип продукта.

**Что отвергли.** Сырое среднее. Порог в три отзыва: он ставил 3,0 при четырёх отзывах выше 5,0 при двух.

**Чем платим.** Новое заведение поднимается медленно. Карточки без отзывов стоят на 3,5 и между собой идут по расстоянию, а без геолокации — по полноте карточки.

**Где в коде.** `backend/src/services/searchService.js` (`buildOrderByClause`). Решение записано в продуктовой стратегии, вне репозитория.

## 3. Как велась работа

Продуктовую логику и решения задаёт основатель; код он руками не пишет — его пишут ИИ-агенты (Claude Code) по письменным правилам работы. Решения записываются с причинами в журнал вне репозитория: 64 действующие записи и 16 архивных, с весны 2026 года.
